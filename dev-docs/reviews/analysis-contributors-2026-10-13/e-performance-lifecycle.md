# Stream E: performance engineering and resource lifecycle (2026-10-13)

Static review of all analysis contributors (631 files in `work/E/files.txt`). Nothing ran on a GPU. Paths are relative
to `modules/experimental/src/` unless prefixed `core:` (`modules/core/src/`), `gpgpu:` (`modules/gpgpu/src/gpu-core/`) or
`ex:` (`examples/deck/`). Line numbers are from the live tree and may drift by a few lines because peers are editing it.
Sub-reports with full tables are in `work/E/E1-compile-rerun.md`, `E2-allocation-readback.md`,
`E3-dispatch-memory-status.md` and `E4-intra-graph-dup.md`. Every finding below was re-read by the coordinator.

## 1. Verdict

Resource lifecycle is clean. There are 4 owned `createBuffer` sites, every owner's `destroy()` covers them, and all 5
custom node `compile()` callbacks return a `destroy`. Transients alias by liveness (gpgpu:gpu-command-graph-compiler.ts:780-820).
The only readback is the explicit `GPURegionStatisticsReadback` ring, and nothing reads back for control flow. Interactive
parameters are mostly buffer writes already: 62 `*-parameters.ts` modules, and 1,348 showcase options are `apply: 'param'`
against 383 `apply: 'compile'`.

The big hidden cost is **pipeline compilation**, and it is worse than the roadmap states for three reasons:
- Library decision 1 assumes override constants share pipelines. They don't, because luma keys pipelines on source plus constants.
- Several shared helpers bake loop-varying values (frontier round, gate-group bit, batch offset, seed, layer) into the WGSL. One reachability call alone compiles 64 relax pipelines where 2 would do.
- Both apps compile synchronously: 522 `.compile()` sites against 0 `compileAsync()`.

Beyond compilation, the gaps are:
- fixed-round loops that keep dispatching at full size after convergence (k-means, location-allocation swap, Weiszfeld median, scan rounds)
- scratch that is not checked against `maxStorageBufferBindingSize`
- one kernel over the WGSL 8 KB private-memory limit

## 4. Roadmap claims that are wrong or stale

- Algorithms roadmap, decision 1: *"no data-dependent numbers baked into WGSL source (uniforms and override constants only), so pipelines are shared across inputs."* This is wrong for overrides. `PipelineFactory` hashes `constants` (core:factories/pipeline-factory.ts:369-377), and WebGPU specialises overrides at `createComputePipeline`, so an override shares the shader module, not the pipeline. The `wgsl-kernel-nodes.ts:243-245` comment and the ripley-envelope comment repeat the half-truth. The rule should be: loop-varying values come from GPU words, and sizes may be overrides.
- Same decision: *"167 showcase files call `graph.compile()`."* The real count is 165 showcase plus 73 explorer files, with 522 call sites and 0 `compileAsync`.
- Decision 4: *"the 3–4 remaining CAS float adds."* Only 1 is in scope (`point-density/point-density-kernels.ts:357`; its specs compare with tolerance). The others are set-once publishes or union-find links, plus `gpu-trace` (out of scope).
- P1 viewshed: *"build the extrema pyramid in-graph and default to `'pyramid'`"* and the review note *"the extrema pyramid has to be built in-graph."* The in-graph build already exists (`gpu-terrain/terrain-analysis/gpu-terrain-viewshed.ts:475-490`). Only the default (`:510`, `'march'`) remains, so the item is now S: flip the default after an A/B.
- P1 scan-statistic: *"removes an O(Z²) cliff."* The cliff is Z²·⌈L/32⌉, roughly cubic (E-13).
- P2 location-allocation: *"Greedy-only → standard interchange quality."* A swap loop already exists (`gpu-location-allocation.ts:290`, 100 iterations by default). What remains is gating (E-08) and swap quality.
- P0 `GPUKMeans` empty-cluster reseed: the code documents the opposite contract ("a center that never received a point keeps its previous position", `gpu-kmeans.ts:139-142`). Decide which is the API before implementing.
- The perf round lists *"Tile relaxation: about 640 nodes per relaxation"* as a graph-size cost only. Those nodes also compile 20 pipelines per relaxation through the baked gate slot (E-03).

## 5. Unverified suspicions

- **Actual pipeline counts.** The counts in E-01–E-07 come from reading the source. They are confirmed by a dry graph build that counts unique `(source, constants)` per compiled graph, for example with `debugFactories` logs or the `PipelineFactory` cache size after `compile()` on one GPU spec.
- **The E-10 limit.** Dawn/Tint may not enforce the 8,192 B private limit, in which case E-10 is a spill and not a failure on Chrome. WebKit is reported to enforce it. A compile-only pipeline creation at 64 classes would settle it.
- **AZP private bytes.** The candidate kernel's total private bytes at 65,536 rows (the bitset plus locals) may exceed 8,192 B.
- **Regression diagnostics headroom.** `spatial-regression-diagnostics.ts` holds six p² matrices, about 6.3 KB at p=16, so headroom is thin if p can reach 16 there.
- **Luma primitives.** Trusted primitives (GPUSort/scan) may bake per-pass shifts. That would multiply the rank loops in E-06. Not reviewed, per the brief.
- **Driver cache.** Chrome's on-disk pipeline cache may hide part of E-01–E-07 on warm reloads but not on first load. Confirm with a cold-profile timing.

## Quick A/B candidates (one GPU spec at a time, cheap)

1. **Scene load: sync compile vs `compileAsync`.** Run one showcase network scene (isochrones or job accessibility) and one terrain scene (watersheds). Measure wall-clock to first frame and the longest main-thread task.
2. **Reachability round cursor.** Patch `createFrontierRoundNode` to read the round from a GPU word. Then compare `GPUNetworkReachability` compile time and pipeline count at `maxIterations` 64 (`gpu-network-accessibility-bench.spec.ts`). Expect 64 → 2 pipelines with the same encode time.
3. **Cost-matrix padded batch stride.** Pad `laneCount*nodeCount` to a multiple of 64 and count pipelines and compile time for 1000 rows on the 48×48 bench grid.
4. **Raster gate slot as data.** Patch `GROUP_OFFSET` to a status word in `raster-relaxation.ts`. Then compare compile time and pipeline count for `GPUTerrainFlow` (fill + flats) on 2048², and check that GPU time is unchanged.
5. **K-means gating.** Put a `condition:` on `state[0]` for each Lloyd iteration. Run n=1e6, k=8, 64 iterations, on data that converges in about 10. Expect about 6x less GPU time. Also check pipeline count before and after moving `ROUND_SEED` to a word, at k=64.
6. **Location-allocation swap gating.** Use the default 100 iterations on a converged instance and compare dispatches executed and GPU time.
7. **Pycnophylactic.** Gate the iterations instead of copying, at 2048² and 100 iterations, with convergence near 20.
8. **Pearson/Gamma two-stage reduction vs single workgroup** at 1e6 rows, k=8.
9. **Scan-statistic `nearest` node time alone** at Z = 1024, 2048 and 4096, to confirm the cubic growth before the grid-kNN work.
10. **Cumulative viewshed** at 1024² with 200 observers: compile time with `FIRST_OBSERVER` baked vs read from a params word.
11. **Join-count atomics.** Workgroup reduction vs per-row atomics in `GPUGlobalSpatialStatistics` at 1e6 rows.
12. **Point-spatial-query bind-group reuse.** CPU encode time over 1000 encodes, before and after the binding cache.
